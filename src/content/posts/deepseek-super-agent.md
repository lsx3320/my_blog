最近 DeepSeek 又放了个很值得玩的东西出来，叫 **Super Agent**。

一句话说清楚它干嘛的：把你从"繁琐的工作流"里解放出来——事情来了，Agent 自动识别、自动分配、自动执行，最后**人只做审核这一件事**。

它的机制就三个词：**接单 → 干活 → 人工审核**。

这套东西我本地真机跑了一遍，从装、到配信息源、到让它在 GitHub 上自动接了一个 issue、自己改代码、自己开 PR，全程截图。下面把整个过程摊开讲。

> 声明一下：这是 DeepSeek 官方开源的研究原型（`deepseek-ai/dsh-superagent-prototype`），跑在 DeepSeek Harness 之上。它跟我平时用的 DeepSeek Harness 桌面端是**两个独立的宿主**——Super Agent 是专门用来"自动接活"的那一套。

---

## 先看它到底长什么样

装好之后，会单独起一个 Web 面板（默认 3084 端口），顶部有个专门的 **Superagent** 入口。它跟普通桌面端长得像，但多了一个独立的"主 Session"——也就是那个**协调者（orchestrator）**。

![主界面协调者](/posts/superagent/01-主界面协调者.png)

注意看中间这段对话，它已经自己跑完了一单：

- 「收到执行请求」× 几条
- 「Ticket 已受理：在 README.md 末尾添加该行并开 PR，只改动这一个文件」
- 「已交付：PR #2 …仅改动该文件，已通知原会话」

**这就是完整闭环的证据**：任务进来 → 协调者受理 → 分配 → 执行器干完 → 提 PR → 通知原会话。全程我没敲一行代码。

## 核心一：活从哪里来（信息源）

Super Agent 是"自动接活"的，那活是谁派的？这就是它第一个要配置的东西——**信息源**。

官方现在支持两个：**GitHub** 和**飞书**。而且是**双通道**——信息源既能给 Agent 派任务，Agent 也能把结果回复回去。

![来源配置](/posts/superagent/03-来源配置.png)

我这次把两个都开了：飞书（运行中）和 GitHub（运行中）。在飞书群里 @ 一下机器人就能派活；在 GitHub 上建 issue 也能派活。

### 飞书到底是怎么"接活"的？一个真实例子

光看配置页有点抽象，我直接进飞书工作台，把我那次真实派活的消息列表截出来看：

![飞书消息列表派活闭环](/posts/superagent/09-飞书消息列表派活闭环.png)

这张图里能看到完整的闭环，四个会话串成一条线：

1. **「用户926759」（我）** 发了一条私聊：*"请帮我在 README.md 末尾加一行…只改这一个文件，改完开一个 PR"*
2. **「dsh-superagent」（智能体）** —— 这就是那个机器人，它接到了这条消息
3. 紧接着下面就是它的**回复**：*"已完成：PR #2 …可以审阅"*
4. 旁边还有「开发者小助手」「飞行社」这类其他机器人，说明飞书里机器人和人混在一个消息流里，**机器人跟人一样是通过消息来对话的**

注意一个细节：飞书里这个机器人叫 **「dsh-superagent」**，标签标的是「智能体」。也就是说，飞书群或私聊里 **@ 一下它，就能把活派出去**。等它干完，会回到**原会话**里回你一句"已完成，PR 在这里"，你点开就能审，全程不用离开飞书。

这就是飞书信息源的价值：**你不用打开任何面板、不用切换工具，就在日常聊天的飞书里，像叫同事干活一样给 agent 派活、收结果。** 对已经把飞书当工作主阵地的团队来说，这个入口几乎零学习成本。

## 核心二：谁能派活（准入策略）

这是最容易踩坑、也最关键的一环。这里有个铁律：**机器人账号得是单独一个账号，不能用你自己的大号**——因为 agent 写的东西全都会挂在这个账号名下，你不想自己的 commit 记录里混进一堆机器提交。

配置里有个「评估」页，专门管这个。它决定了一件事：什么样的请求会被"接单"，什么样的只被"记录"。

![评估准入策略](/posts/superagent/04-评估准入策略.png)

上图能看到一条真实的决策记录：

> 「名单里的人明确请求，由主 Session 接单」

翻译成人话：**只有在你白名单里的人，@ 了机器人，它才动手干活**。不在名单里、或者没 @ 它，它就只记录、不干活。这套"准入"逻辑，就是防着 agent 乱接活、乱改东西的安全阀。

## 核心三：执行与并行

「执行」页管的是 agent 干活时的资源。

![执行配置](/posts/superagent/05-执行配置.png)

能看到「执行器运行中」「执行中 0/3」——**最多并行 3 个工单**，这个数可以改。执行用什么模型、跑在什么环境、允许它执行哪些命令，都在这里配。

整套设置说白了就三条：**我从哪里接单、我可以接谁的单、我用什么模型来干活**。

## 核心四：提示词才是灵魂

这是我觉得 Super Agent 最妙的地方。它把整个工作流拆成"事件流"——每一个阶段都是一个可自定义的提示词段落。

![提示词配置](/posts/superagent/07-提示词配置.png)

分成两块：

- **团队约定**：沟通方式（怎么通知人、消息怎么写）、工单范围（什么时候继续、什么时候暂停交草稿）、交付要求（PR 证据、自动合并条件、提交作者）
- **内置段落**：共享约定、主 Session 角色、执行器角色、订阅、回复与确认、路由

这里有个很有意思的设计：**为什么 PR 长这样、带不带改前改后的截图，全都可以自己在提示词里定**。比如你可以写死"提交 PR 时带上改前改后的截图"。上图里「交付要求」就标了个**「已改」**，说明这段是被自定义过的。

## 完整跑一遍：从 issue 到 PR

最后串起来看全过程。这是我在 GitHub 上建了个 issue 派活之后，它自动干出来的：

![PR 提交](/posts/superagent/08-PR提交.png)

- PR 标题：`docs: note README is used for dsh-superagent smoke tests`
- 改动：**只改了 README.md**，末尾加一行 `This repository is used for dsh-superagent smoke tests.`
- 分支名：`agent/readme--smoke-note-48b15e1f7bee`（agent 前缀，机器自动生成的）

注意 PR 正文那句 **"This is by an automated agent, not a human"**——它在明明白白告诉你：这是 agent 干的，不是人。

有意思的是，这次改动是纯文本，所以 PR 里写的是 "No UI change, so no before/after screenshots apply"（无 UI 改动，不适用前后截图）。这正好反过来说明了：**只有涉及 UI 的改动，它才会自动做改前/改后的浏览器截图对比**。

## 一句话总结

Super Agent 的骨架真的不复杂，就三步：

1. **接单**——从 GitHub/飞书，按准入名单判断要不要接
2. **干活**——协调者分发，执行器用配置好的模型和环境去改代码、提 PR
3. **审核**——人只看 PR，低风险的甚至可以自动合并 + 快速回滚兜底

再复杂的自动化系统，无非是把这三步里的某个环节打磨得更准——多接几个来源、多加几道 code review、多放几个 agent 交叉检查。

最后说个我自己的判断：**模型越强、写的代码越多、提的 PR 越多，人就越看不过来**。所以把注意力从"写"挪到"审"，把低价值的重复劳动丢给 agent，可能才是接下来用 AI 的正确姿势。

## 这东西，放你团队里怎么用

讲两个具体的场景，你就能判断它跟你有没有关系。

**场景一：那个永远没人愿意干的"改文案"活。**

假设你们团队刚改了个产品名，从"旧名"换成"新名"。这个改动要同步到十几个仓库的 README、官网的几行介绍、几个 config 里的默认值——没难度，但琐碎，谁接谁烦。

以前的做法是：有人在群里喊一嗓子，或者开个 issue 挂着，等哪个倒霉同事有空了去挨个改。快的半天，慢的拖一周。

现在你把这件事丢给 Super Agent。你在飞书群里 @ 它一句："产品名从 A 换成 B，把所有仓库里的 A 都改掉，各开一个 PR。"接下来就是它的事了——它自己拉代码、自己找所有出现 A 的地方、自己改、自己给每个仓库提一个 PR。你该干嘛干嘛，过一会儿飞书里收到一串"已完成 PR #1、#2、#3"的通知，你点开扫一眼 diff，对的就合并。**整个过程你只动了两下：发一句需求、点几个"合并"。**

这就是它真正的价值：**不是替你写代码，是替你把"等别人、找人、盯着人干"这套沟通和搬运的活干完了。**

**场景二：那种"明确到一句话、但得天天重复"的小改动。**

比如每天都要干的：给新加的服务补一个监控配置、把某个依赖升级到安全版本、给接口补个单测。这种活的特点是——**需求一句话能说清，但一周能冒出五六个，积少成多很耗人。**

把这类活都甩给它：需求从 GitHub issue 或飞书进来，它按你设好的准入名单判断"这单我接不接"，接了自动开工作区干活、自动提 PR，你只在最后审核。设置里还能把"并行工单数"调到 3，让它同时处理三个这种杂活。

**反过来，什么活别给它：**

那种"帮我设计一下整个系统的架构"、"这个线上 bug 你看着修"的开放式、高风险活，现在别指望它。这类任务边界不清晰、判断错了代价大，它现在还兜不住，得人自己上。

**所以一句话结论：** 它现在能干的，是那些**"一句话能说清、错了也好改、量还不少"的小活**——把这些从你的时间里抠出来，把人腾去干真正需要动脑子的部分。它不是"替你写代码的实习生"，更像一个**"随叫随到、还不用你盯着的杂活外包"**。落地面不宽，但在"小活自动化"这件事上，确实能省下实打实的时间。
